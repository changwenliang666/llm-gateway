# 第 7 课：限流、熔断与异常处理

### 1. 本节课我们要学什么？

把三件容易混在一起的事拆开：限流是「这个模型最近 60 秒是不是太多了」，熔断是「这个模型上的这个账号是不是正在连续失败」，异常处理是「各种失败最后变成哪一种 HTTP」。学完你应该能拿着状态码反推它是在选账号时被熔断跳过或挡下的，还是限流在选定账号之后挡下的，还是上游回来的，还是网关等不及了。

算法的横向对比在第 8 课，文件 `07-核心设计模式与技术原理.md`。这一课先把本项目真正执行的那条路走通。

### 2. 先讲一个生活中的例子

奶茶店有两套完全不同的规定。

限流像门口的号牌，但号牌看的是「从现在往回 60 秒」，不是墙上的整点。店规定任意 60 秒最多做 60 杯。第 61 杯如果还落在这 60 秒里，人在门口就被请走，店员还没开始做，也不算这杯做砸了。最早那一杯满 60 秒之后，名额才空出来，不会因为时钟跳到下一分钟就突然再放 60 杯。

熔断像每台机器自己的保险丝，也像店长只暂停这一台机器。连续五杯都从 2 号机做出了怪味，店长把 2 号机停 30 秒。1 号机还在做。这 30 秒里不是「太忙」，是「再打这台机器多半还是失败，先别打它」。30 秒后不是永远停着，而是先用这台机器做一杯试试。试成功，这台机器恢复。试失败，再停 30 秒。两台都停了，店才暂时不接单。

保险丝如果熔断后永远不换，这台机器就永久停工，那不叫保护，叫坏掉。所以必须有「试探恢复」。

异常处理像店员怎么回答顾客。有的是店自己的告示：「今天这台机器暂停」「这一分钟满了」。有的是把工厂的退货单原样递出来：工厂说参数不对，店员不改写成自己的告示。

### 3. 为什么需要这个技术？

没有限流，一个脚本可以把一家模型的配额在一分钟内打光，后面的正常业务全部失败，账单也异常。没有熔断，上游已经在连续 500，网关仍把每个用户的请求都送上去，线程堆在超时上，故障被放大。

两者替换不了对方。模型很健康但流量太大，该限流，不该熔断。流量不大但连续超时，该熔断，限流计数可能根本没满。

限流是模型级的。`deepseek-flash` 的 RPM 打满，不影响 `qwen-max`，也不按账号拆开。熔断是账号级的。同一个模型上账号 A 连续失败，只打开 A；账号 B 还能被选中。一个账号的 Key 无效，靠的是 401 换下一个账号，不是把这个账号熔断。401 和上游 429 故意不记入熔断失败，因为那更像钥匙或对方限流，不是这个账号背后的服务挂了。

### 4. 技术原理

先看限流在本项目里的具体算法，再用数字走一遍。

它是滑动窗口。键是 `llm-gateway:rl:{模型id}`，一个模型一份有序集合。每次放行写一条成员，分数是当时的毫秒时间，成员正文就是这次的 `reservationId`。判断前先删掉年龄大于等于 60 秒的成员，再用条数和 RPM 比较。`RateWindows.WINDOW_MILLIS` 就是这 60000 毫秒。键的过期时间是 120 秒，模型闲下来以后 Redis 不会一直留着空集合。网关不按 Token 拒绝。`models.tpm` 即使有值也不传入这条脚本。

假设 RPM 设为 60，而且这 60 次都还在最近 60 秒里。

| 请求 | 窗口里已有条数 | 判断 | 结果 |
| --- | --- | --- | --- |
| 第 1 次 | 0 | 0+1 不大于 60 | 放行，写入 1 条 |
| 第 60 次 | 59 | 59+1 不大于 60 | 放行，写入后共 60 条 |
| 第 61 次 | 60 | 60+1 大于 60 | 返回 0，不写入 |

第 61 次在 `RedisModelRateLimiter.inspect` 里变成 429，「模型请求超过限制」。如果最早那一条已经满 60 秒，它会先被删掉，窗口里只剩 59 条，第 61 次就能进。时钟从 12:00:59 跳到 12:01:00 不会单独清零。12:00:59 放进的 60 次，在 12:01:00 仍然占满额度。

模型上即使保存了 TPM，也不会因为估算 Token 太大而返回 0。文生图和文生视频没有稳定的 Token 用量，网关不再做这层判断。供应商自己返回 HTTP 429 时，调用方看到的是上游状态码和正文。还没写出字节、并且还有另一个未熔断账号时，会先换那个账号再试一次，RPM 不加第二次。

`RateWindows.estimate` 用 JSON 字节数除以 4，至少 1。它只在成功且适配器没有读到 `usage.total_tokens` 时，累加到 `consumed_tokens`。流式和视频经常走这条估算。累加失败只打日志。它不改限流窗口。

熔断的状态存在 Redis 哈希 `llm-gateway:cb:{模型id}:{账号id}`。同一个模型的两个账号是两把键。字段有 `state`（`closed`、`open`、`half`）、`failures`、`openedAt`、`probes`、`probeUntil`。没有后台线程每秒去看。下一次选到这个账号并执行 `acquire` 时，如果发现打开的时间已经超过冷静期，这条 Lua 自己把状态改成半开。别的账号不会读这把键。

默认参数在 `GatewayProperties.Circuit`，可用环境变量覆盖：连续失败 5 次打开，冷静 30000 毫秒，半开同时只允许 1 个试探，试探租约 120000 毫秒。租约是为了防止拿到试探名额的进程中途死掉，名额永远不还。120 秒后，新的请求可以把过期名额清掉再试。

`acquire` 的返回码：0 拒绝，1 正常关闭状态放行，2 半开试探放行。Java 侧分别变成 `Permit.rejected()`、`Permit.closed()`、`Permit.probe()`。

### 5. 放到我们的项目中

熔断发生在 `RoundRobinAccountLoadBalancer` 选账号的时候。限流仍在 `ModelAdmission.enter`。对话、视频创建、视频查询都走这两处。新的厂商适配器不应该自己再写一套。

```java
Selection selected = loadBalancer.select(route);
Permit permit = admission.enter(route, selected.account().accountId(), selected.circuitPermit(),
        caller, estimatedTokens);
```

`select` 里对每个候选账号调用 `breaker.acquire(modelId, accountId)`。返回拒绝就换下一个，不轮换这个账号的 Key。全部拒绝才抛 503，「模型暂时不可用」。这时限流 Lua 不会执行，所以不消耗 RPM。负载均衡开启时，账号游标在扫描之前已经 `INCR`。负载均衡关闭时只检查最小账号，它拒绝就 503，不扫描后面的账号，也不推进账号游标。

`enter` 只做模型级限流。拒绝或 Redis 限流不可用时，`quietlyRelease` 归还这个账号的半开名额，并且不调用 `fail`。限流拒绝不计熔断失败。账号和 Key 的游标在 `select` 里已经加过。

`CallerContext` 带了客户端地址和 `X-Gateway-Client-Id`，但 `inspect` 的实现不用它们。没有按调用方限流。头只是预留，避免以后改方法签名。讲当前行为时不要说「已经按 client id 限流」。

调用结束后的 `finish`：

| `CallOutcome` | 状态码 | 熔断动作 | Token |
| --- | --- | --- | --- |
| `SUCCESS` | 200 到 399 | `succeed`，失败清零，状态关闭 | 成功才累加 `consumed_tokens`。有真实用量用真实值，没有就用估算。不回写限流窗口 |
| `FAILURE` | 大于等于 500 | `fail` | 不累加 |
| `NEUTRAL` | 其他，主要是 4xx | `release`，半开名额归还，不增加失败 | 不累加 |

超时和连接失败没有 `InvokeResult`，不走 `finish`，走 `admission.fail`。记在已经选中的那个账号上。

换到另一个账号之前，`admission.observe` 先按前一个账号自己的 HTTP 结果回写它的熔断。`finish` 只处理最后这个账号。同一账号换下一把 Key 不调用 `observe`，只按最后一次 `finish`。

账号游标的 Redis 失败发生在拿到熔断名额之前，没有名额可还。Key 游标的失败发生在 `acquire` 之后，`RoundRobinAccountLoadBalancer.admit` 自己 `release`，只还名额，不记失败。账号并没有被调用。

`fail` 在 Lua 里的规则：如果这次是半开试探，一次失败就立刻回到 `open`，并重计 `openedAt`。如果是关闭状态，`failures + 1`，达到阈值才打开，并把失败计数清零后开始冷静。2xx 的 `success` 命令把状态、失败、试探全部归零。

开关关掉限流，或 RPM 不是正整数时，`inspect` 直接返回空，不访问 Redis。只配置了 TPM 也等于不计数。熔断没有按账号关闭的开关。每个模型上的每个可调度账号都有一份状态，只是没失败时一直是关闭。打开阈值、冷静时间和试探数仍是进程级环境变量，不是每个账号各存一套。

测试里有 `AllowAllRateLimiter` 和 `AllowAllCircuitBreaker`，它们没有 `@Component`。生产不会把它们注入进去。生产实现是带 `@Component` 的 Redis 版本。你在 IDE 里「查找实现」会看到两个，运行时要看谁被 Spring 创建了。

### 6. 核心代码逐段讲解

限流判断的核心在 `src/main/resources/redis/rate-limit.lua`，不是在 Java 的 if 里。Java 传入当前毫秒、RPM 上限、这次的 `reservationId` 和过期秒数。

```lua
if rpmLimit > 0 and (count + 1) > rpmLimit then
  return 0
end
```

`count` 是删掉过期成员之后的条数。为什么用 Lua 而不是先读再写？两个网关进程可能同时读到 59 条，都认为可以放行，结果变成 61 条。Lua 在 Redis 里原子执行，读、删过期和写入不会被另一条命令插队。超限时 `ZADD` 不执行。

熔断打开期间的判断在 `circuit.lua` 的 `acquire`：

```lua
if state == 'open' then
  local openedAt = tonumber(redis.call('HGET', key, 'openedAt') or '0')
  if now < openedAt + openMs then
    return 0
  end
  redis.call('HSET', key, 'state', 'half', 'probes', '0', 'probeUntil', '0')
  state = 'half'
end
```

冷静期没到，返回 0，Java 抛 503。到了，先改成 `half`，再往下看名额。半开名额没满就加一，写下租约截止时间，返回 2。

异常怎样变成响应，集中在 `GatewayExceptionHandler`。

- 捕获 `GatewayException`：响应还没提交，就按异常里的状态码写出 `ErrorResponse`。
- 响应已经提交：不能再改，打 warn 后返回。流式写到一半超时就是这条路。
- 捕获其他没想到的 `Exception`：记 error 日志，能写的话返回 500，「网关内部错误」，`type` 为 `server_error`。

上游的 400 不是 `GatewayException`。它是 `InvokeResult`，状态码原样写回，正文原样写回，`type` 那套结构不会套上去。你要会区分这两种 400：一种是网关在发车前抛的，JSON 里有 `error.type`；一种是厂商返回的，长什么样由厂商决定。

数据库查询失败：`DbModelCatalog` 没有把 SQL 异常收成业务文案，它会变成未处理异常，走到上面的 500。任务表的失败则在 `DbTaskBindingStore` 里被收成 503，「任务绑定不可用」。两种数据失败的表现不一样，排查时要看是选路阶段还是记账阶段。

模型配置错误：适配器名字写错是 400。地址写错导致连不上，是发出去之后的 502。地址能连上但路径被厂商拒绝，是厂商的 HTTP 状态，原样返回。

不同厂商的错误 JSON 不一致：网关不尝试统一它们。只有网关自己产生的错误才有固定的 `error.message` 和 `error.type`。

请求重复提交：没有幂等键。文本每次 UUID 不同，连点两次就是两行、两次上游调用、两次限流计数。视频如果上游返回同一个 `task_id` 再次插入，SQL 只更新状态，保留第一个账号。调用方自己重试创建，通常会得到新的上游任务号，那就是新的一行。网关不会替你合并「同一句话」。

### 7. 配图理解

准入和调用之后的熔断回写：

```mermaid
flowchart TD
    in[请求已有 ModelRoute]
    pick{按账号 acquire}
    reject[503 模型暂时不可用]
    rl{模型级限流 Lua}
    tooMany[429 并归还这个账号的半开名额]
    call[调用上游]
    http{这个账号的结果}
    ok[succeed 清零这个账号的失败]
    bad[fail 累加或重新打开这个账号]
    mid[release 不计失败]
    down[异常路径 admission.fail]

    in --> pick
    pick -->|这个账号打开| pick
    pick -->|全部打开| reject
    pick -->|选定| rl
    rl -->|超限| tooMany
    rl -->|放行| call --> http
    http -->|2xx 或 3xx| ok
    http -->|5xx| bad
    http -->|4xx| mid
    call -->|超时或连接失败| down
```

逐步看。

1. 熔断 503 发生在选账号的过程中。一个账号打开只会让选择跳到下一个。429 在账号已经选定之后。全部打开时限流 Lua 不执行。
2. 4xx 不是失败也不是成功。半开时要把试探名额还掉，否则一个 400 会把这个账号的恢复探测卡死。
3. 超时不在 `http` 那个判断里，它是异常，单独进入当前账号的 `fail`，并且不换账号。

一次熔断从健康到恢复，用默认阈值走数字。

1. 状态是 `closed`，`failures` 为 0。
2. 连续 5 次超时。每次 `fail`，失败数变成 1、2、3、4。第 5 次达到阈值，状态改为 `open`，`openedAt` 写成现在，失败数清零。
3. 之后 30 秒内再选到这个账号，`acquire` 返回 0，选择跳到别的账号。别的账号都打开时，调用方才看到 503。这些拒绝不再增加失败数，也不增加 RPM。
4. 第 31 秒来了一个请求。Lua 发现冷静期已过，改成 `half`，发出 1 个试探名额，返回 2。
5. 这次上游 200。`success` 把状态改回 `closed`，失败清零。
6. 如果第 5 步仍是超时，试探失败立刻回到 `open`，冷静 30 秒重计。

中间如果试探请求被限流挡下，`enter` 的 catch 会 `release`，名额减一，不记失败。机器既不恢复也不再次熔断。

### 8. 常见误区

- 「429 都是一回事。」网关自己的 429 是模型级限流，JSON 为 `rate_limit_error`，发生在账号已经选定、上游还没打的时候。上游的 429 是厂商说这把 Key 太频繁，正文是厂商的，并且可以触发换账号。熔断不把上游 429 算失败。
- 「熔断打开后要等一个定时任务。」没有定时任务。下一次选到这个账号的请求，就是那个把 `open` 改成 `half` 的人。
- 「限流和熔断的计数在每台机器的内存里。」生产实现在 Redis。否则多实例各计各的，阈值会放大成实例数倍。测试用的内存实现没有注册成 Bean。
- 「5xx 换账号成功之后，前一个账号不算失败。」会算。换账号前 `observe` 给前一个账号记失败，`finish` 只把后一个账号记成成功。两次调用都会写 `model_tasks`。同一账号只换 Key 时不 `observe`，熔断只看最后一次。

### 9. 本节课总结

限流是一个模型滚动 60 秒里的 RPM，超了 429，这次不写入，不计熔断。供应商的 TPM 错误不是这句网关 JSON。熔断是某一个账号连续失败达到 5 次后打开 30 秒，然后用一个带租约的试探决定这个账号恢复还是继续打开。2xx 恢复这个账号，5xx 和超时算这个账号失败，4xx 算中性。网关自己的错误有固定 JSON，厂商的错误原样返回。

### 10. 课后练习

入门：RPM 为 2，最近 60 秒里已经有 2 次放行，第 3 个请求会发生什么？熔断的失败次数会加一吗？

参考答案：第 3 个请求在 `rate-limit.lua` 里因 `(2+1) > 2` 返回 0，Java 抛 429，「模型请求超过限制」。这次不 `ZADD`。抛出前如果占着半开名额会归还。不会 `breaker.fail`。前两次已经各写了一条，第 3 次不加。

进阶：连续 4 次超时，第 5 次上游返回 400。熔断会打开吗？

参考答案：要先看这 4 次超时是不是同一个账号。超时不换账号，但下一次新请求会轮询到别的账号。打在同一个账号上时，`failures` 变成 4，默认阈值是 5。第 5 次若仍是这个账号并且返回 400，400 是 `NEUTRAL`，走 `release`，不调用 `failure` 命令，失败数停留在 4。还要再有一次打到这个账号的超时或 5xx，这个账号才会打开。四次超时如果被轮询拆到两个账号上，可能谁都没到 5。

实战：半开试探已经发出，持有它的进程被杀掉，没有执行 `success` 也没有 `release`。最多等多久，别的请求才能再试探？依据是哪段代码？

参考答案：最多大约等 `probe-lease-ms`，默认 120000 毫秒。`circuit.lua` 在半开分支里，如果 `probes > 0` 且现在已经超过 `probeUntil`，就把 probes 清零，然后允许新的试探。这个时间来自 `GatewayProperties` 的 `probeLeaseMs`，可用 `GATEWAY_CIRCUIT_PROBE_LEASE_MS` 修改。
