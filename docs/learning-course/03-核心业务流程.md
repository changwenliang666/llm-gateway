# 第 4 课：三条真实业务链路

### 1. 本节课我们要学什么？

把文本对话、视频创建、视频查询分成三条路。它们共用选路、熔断、限流和 HTTP 出口，但在「改正文、换不换账号、任务表怎么写」上不一样。学完你应该能看着一个路径，说出会进哪个 Service 的哪个方法，以及哪一步可能把请求挡回去。

这一课把每条链路讲到「类和方法」这一层。流式拷贝在第 6 课展开，限流和熔断的 Lua 在第 7 课展开。第 9 课会把文本这一条按变量走完。

### 2. 先讲一个生活中的例子

同一家打印店做三件事。

印一份文档：你把原文交过去，店员换成印刷厂认识的格式，当场拿回成品。如果这家印刷厂说「这张会员卡无效」，店员可以改用下一张卡再印，只要成品还没交给你。

预约一本相册：印刷要两小时。店员只给你一张取件号，相册还没印好。台账上记下「这张取件号是用 3 号会员办的」。

凭取件号来取：必须用当时办业务的那个会员查，换一个会员，印刷厂说查无此单。同一个会员口袋里如果有两张卡，卡刷失败可以换另一张卡，但不能换会员。

文本对话是印文档。视频创建是办取件号。视频查询是凭号来取。代码里的差别就是从这个业务差别来的，不是为了多写一个类。

### 3. 为什么需要这个技术？

如果查询视频也走普通轮询，任务是账号 A 创建的，查询却轮到账号 B，上游会返回无权或不存在。调用方以为视频失败了，其实只是问错了人。

如果创建视频也等它做完再返回，一个请求会占住网关线程好几分钟。超时预算默认最多 120 秒，视频往往更久。所以创建接口必须异步：上游马上回 `task_id`，网关马上把这个号交出来。

如果文本接口接受视频模型，网关会把一段聊天 JSON 发到视频合成地址，上游返回一串看不懂的错误。所以每个适配器用 `supports` 声明自己接哪些操作，编排层在发车前检查。

### 4. 技术原理

三条链路的公共前半段可以记成一句：读入参，`RouteResolver.resolve`，确认适配器支持这个操作，`ModelAdmission.enter`，然后才选账号。

公共前半段挡下来的结果是网关自己的 JSON。放行之后，上游的状态码和正文尽量原样回去。

分叉点有四个。

操作类型。`AdapterOperation` 这个枚举只有三个值：`CHAT_COMPLETION`、`VIDEO_CREATE`、`VIDEO_QUERY`。`OpenAiChatAdapter.supports` 只认第一个。`DashScopeWanAdapter.supports` 认后两个。

选账号的方式。新的对话和创建走 `loadBalancer.select`。查询先 `bindings.findAccountId(taskId)`，有记录就 `selectKey`，只在那个账号的 Key 之间轮换。

失败后换什么。对话和创建调用 `nextAccount`，换的是下一个账号，并且不再对账号游标做 INCR。查询调用 `nextKey`，只换同一账号的下一把 Key。账号游标不动。

任务表。对话和创建在拿到 HTTP 响应后 `CallRecords.record`，插入一行。查询调用 `CallRecords.refreshStatus`，只更新已有行的状态。查询失败且正文里没有新状态时，不把仍在跑的任务改成 `FAILED`。

### 5. 放到我们的项目中

#### 文本对话

入口：`ChatCompletionController.chat` → `ChatCompletionService.handle`。

业务方可以只传 `message` 字符串，不必自己拼 `role`。网关收成一条 user 消息。其余字段，例如 `max_tokens`、`temperature`，留在 JSON 里原样转发给上游。`stream` 为布尔 `true` 时走 SSE。

挡路一览，按代码实际抛出的位置：

| 你看到的结果 | 在哪抛出 | 会不会打到上游 |
| --- | --- | --- |
| 400 请求体不是合法 JSON / 必须是 JSON 对象 | `JsonBodies.object` | 否 |
| 400 缺少模型名 | `JsonBodies.requiredText` | 否 |
| 400 超时必须是正整数毫秒 | `HeaderTimeoutPolicy.resolve` | 否 |
| 404 模型不存在或已停用 | `RouteResolver.resolve` | 否 |
| 400 不支持的协议适配器 | `RouteResolver.resolve` | 否 |
| 503 没有可用的供应商账号 | `RouteResolver.resolve` | 否 |
| 400 该模型不能用于对话接口 | `handle` 里的 `supports` | 否 |
| 400 message 必须是非空字符串 | `rewritePlainMessage` | 否 |
| 503 模型暂时不可用 | `ModelAdmission.enter` | 否 |
| 429 模型请求超过限制 | `ModelAdmission.enter` | 否 |
| 502 上游连接失败 / 504 上游调用超时 | `UpstreamClient.send` | 已经尝试连接或已经在等 |
| 上游自己的 4xx/5xx 正文 | 原样写回 | 是 |

成功时，调用方看到的是上游 JSON，常见形状是 `choices[0].message.content`。网关不把这段文字再包进自己的对象。

#### 视频创建

入口：`VideoController.create` → `VideoSynthesisService.create`。

这里不把 `message` 收成聊天消息。`input`、`parameters` 原样留给适配器。`wan2.6-t2v` 和 `wan3.0-video` 的分辨率字段不同，网关不解析它们，错了由上游返回。两个模型共用 `DashScopeWanAdapter`，代码里没有 `if (模型名是 wan2.6)`。

适配器在创建时额外加请求头 `X-DashScope-Async: enable`。没有这个头，百炼会把调用当成同步接口并拒绝。地址仍是模型行上的完整 `base_url`。

上游马上返回的是任务，不是成片，形状类似：

```json
{
  "output": {
    "task_id": "任务 ID",
    "task_status": "PENDING"
  }
}
```

`CallRecords.record` 优先用 `output.task_id` 当 `model_tasks` 的主键，状态优先用 `output.task_status`。后面的查询靠这个主键找回账号。

创建如果第一次是 401、429 或 5xx，并且还有另一个账号，会换账号再创建一次。两次都记账。上游若给出两个不同的任务号，表里就是两行。调用方最终只看到第二次的正文。这一点要在业务上说清楚：换账号意味着上游可能已经收下了第一次的任务。网关没有调用上游的取消接口。

#### 视频查询

入口：`VideoController.query` → `VideoSynthesisService.query`。

路径上的 `taskId` 来自创建响应的 `output.task_id`。查询参数 `model` 必填，因为任务号只是一串字符，看不出该用哪一行的地址和协议。缺了是 400，「缺少模型名」。文本模型作为 `model` 时是 400，「该模型不能用于视频查询」。任务号为空或包含 `/`、`\` 时，`TaskUris.query` 返回 400，「任务 ID 不合法」。这是为了防止任务号把 URL 路径带跑。

查询 URL 不用合成地址。`TaskUris` 只借用 `base_url` 的协议和主机，路径换成 `/api/v1/tasks/{taskId}`。例如合成地址是 `https://dashscope.aliyuncs.com/api/v1/services/aigc/video-generation/video-synthesis`，查询会打到 `https://dashscope.aliyuncs.com/api/v1/tasks/任务号`。

账号选择：

```java
first = bindings.findAccountId(taskId)
        .map(accountId -> loadBalancer.selectKey(route, accountId))
        .orElseGet(() -> loadBalancer.select(route));
```

表里有记录，就锁回那个账号。该账号已经停用或不在这次快照里，`selectKey` 抛 503，「创建任务的账号已不可用」，不会悄悄改投别人。表里没有记录，才退回普通的 `select`。这是任务记录丢失后的补查，不是正常路径。

查询失败时，`nextKey` 只有在同一账号至少两把 Key 时才有值。不会调用 `nextAccount`。

查完后 `CallRecords.refreshStatus`。正文里有 `output.task_status` 就更新。没有这个字段但 HTTP 是 2xx，记成 `SUCCEEDED`。都没有，就不调用 `updateStatus`，避免一次 400 把仍是 `RUNNING` 的任务改成失败。

成片地址在上游正文里。网关不下载视频，也不另做一层封装。

### 6. 核心代码逐段讲解

视频和对话共用准入，但查询的 Token 估算写死为 1。看 `VideoSynthesisService.query`：

```java
Permit permit = admission.enter(route, CallerContext.from(request), 1);
```

查询没有大段 JSON 可估算，进入限流时仍传 1。这个数字只在成功且没有真实用量时累加到 `consumed_tokens`，不参与拒绝。RPM 按这一次查询加 1。创建视频的累计同样用正文的字节估算，和对话一样。限流窗口只数请求条数。

对话的重试和视频创建的重试形状相同，差在操作类型。对话这段是：

```java
result = call(adapter, command(selected, body, timeout, stream), response, selected);
if (result.retryable() && !result.committed()) {
    Optional<Selection> next = loadBalancer.nextAccount(route, selected);
    if (next.isPresent()) {
        result = call(adapter, command(next.get(), body, timeout, stream), response, next.get());
        selected = next.get();
    }
}
```

`retryable` 为真的条件在 `JsonBodies.retryableStatus`：状态码是 401、429 或大于等于 500。`committed` 为真表示字节已经给了调用方，禁止再试。`next` 为空表示快照里少于两个账号，只能把第一次的结果交出去。

`call` 方法先 `adapter.invoke`。若在拿到 HTTP 状态之前就失败，例如超时，先 `CallRecords.recordFailure` 记一行 `FAILED`，再把异常抛出去。外层 `catch` 再 `admission.fail`。所以超时会同时留下任务行和一次熔断失败。查询方法没有走这个 `call`，超时发生在 `query` 自己的 try 里，只做 `admission.fail`，不插入新行，也走不到 `refreshStatus`。这是代码上的真实差别，不是遗漏文档。

还有一个要正视的行为：`call` 里上游已经成功，但 `CallRecords.record` 写库失败时，异常抛到外层，外层一律 `admission.fail`。也就是说，任务表不可用会被记成当前账号的一次熔断失败。当前代码就是这样。优化方向是把「没打到账号」和「账号调用失败」分开，写库失败不要调用 `breaker.fail`。现在还没有分开。

### 7. 配图理解

三条链路在「选账号」和「记账」上分叉：

```mermaid
flowchart TD
    start[请求进入对应控制器]
    common[读入参并 RouteResolver.resolve]
    op{适配器支持这个操作吗}
    admit[ModelAdmission.enter]
    kind{哪种操作}
    sel[select 选账号和 Key]
    lock[有任务记录则 selectKey]
    call[适配器 invoke]
    retryAcc{401 429 或 5xx 且未写出}
    nextAcc[nextAccount 再试一次]
    retryKey{同一账号还有别的 Key 吗}
    nextKey[nextKey 再查一次]
    save[record 插入 model_tasks]
    refresh[refreshStatus 只更新状态]
    back[把尚未写出的正文交还调用方]

    start --> common --> op
    op -->|否| bad[400 协议不匹配]
    op -->|是| admit --> kind
    kind -->|对话或创建| sel --> call
    kind -->|查询| lock --> call
    call --> retryAcc
    retryAcc -->|对话或创建且有下一个账号| nextAcc --> save
    retryAcc -->|查询且有下一把 Key| nextKey --> refresh
    retryAcc -->|不再试| save
    save --> back
    refresh --> back
```

这张图是简化过的。对话和创建在 `call` 内部就已经 `record`，不是全部堆到最后。查询成功路径不经过 `record`。看图时抓住分叉，精确顺序以第 9 课的文本追踪和 `VideoSynthesisService` 源码为准。

图下面再补三句。

1. 协议不匹配在选账号左边，上游和游标都还没动。熔断拒绝发生在选账号的过程中，打开的账号不会推动它的 Key 游标。限流拒绝在账号已经选定之后，上游还没打。
2. 对话、创建的第二次尝试叫 `nextAccount`。查询的第二次尝试叫 `nextKey`。
3. 交还调用方是最后一步。在此之前，非流式正文一直在 `InvokeResult.body` 这个字节数组里。

### 8. 常见误区

- 「视频查询会再插入一行 `model_tasks`。」正常不会。插入发生在创建和文本调用。查询只 `updateStatus`。主键冲突时，插入语句本身也只更新状态、保留第一次的账号，见 `ModelTaskMapper.xml` 的 `ON DUPLICATE KEY UPDATE`。
- 「创建接口会轮询到视频完成。」不会。适配器注释写明不循环查询。完成态靠调用方再打 GET。
- 「三条链路有三套熔断。」没有。都进 `ModelAdmission`，状态按「模型 id + 账号 id」存在 Redis。同一个模型的两个账号各有各的状态。一个视频模型的某个账号熔断，不会让 `deepseek-flash` 一起 503，也不会让这个视频模型的其他健康账号一起 503。
- 「图像生成是视频适配器的一种。」不是。仓库里没有图像操作枚举，也没有图像控制器。

### 9. 本节课总结

三条链路共享「先准入、再选路执行、适配器不决定重试」。文本当场返回内容，失败可以换账号。视频创建只拿任务号并记住账号。视频查询凭任务号回到那个账号，最多换一把 Key。能把这三句和对应的方法名说出来，业务链路就通了。

### 10. 课后练习

入门：为什么查询接口除了路径里的任务号，还要查询参数 `model`？

参考答案：任务号是百炼返回的字符串，里面没有适配器名，也没有 `base_url`。网关要靠模型名去 `models` 表找到协议和主机，才能拼出 `/api/v1/tasks/{taskId}`。缺 `model` 时 `VideoSynthesisService.query` 开头就抛 400，「缺少模型名」。

进阶：同一次视频创建，第一次上游 500，第二次换账号后 200。`model_tasks` 里可能有几行？熔断按哪一次更新？

参考答案：两次 `call` 都会 `record`。第一次若没有 `output.task_id`，主键是 UUID，状态按 500 记成 `FAILED`。第二次若有新的 `output.task_id`，再插入一行。所以通常是两行。只有两次碰巧写出同一个主键时，后一次才变成更新状态、保留第一个账号。换账号之前 `admission.observe` 会给第一个账号记一次失败。`admission.finish` 只处理第二个账号的 200，把第二个账号的失败次数清零。第一个账号的失败留在它自己的键上。调用方只收到第二次的正文。同一账号只是换下一把 Key 时不走 `observe`，熔断只按最后一次 `finish`。

实战：一个 `PENDING` 的任务，查询时上游返回 400，正文里没有 `output.task_status`。表里的状态会变成 `FAILED` 吗？

参考答案：不会。`CallRecords.refreshStatus` 只有在读到 `task_status`，或 HTTP 为 2xx 时才更新。400 且没有状态字段，方法直接返回，旧的 `PENDING` 保留。代码注释写的就是：避免一次参数错误把仍在跑的任务记成失败。
